# ユーザ致命的バグ — 重大度定義（一般）

プロダクト横断で使う判定軸。リポジトリ固有の画面名は例示に留める。

## 一文定義

**ユーザ致命的バグ** = ユーザーがプロダクトの主要価値を安全に得られなくなり、データ・金銭・プライバシー・業務継続に実害を与え、回避が困難で、放置すると信頼や収益に深刻な損害を与える不具合。

## 判定軸

| 軸 | 致命的とみなされやすい例 |
|----|--------------------------|
| 利用不能 | ログイン不可、起動直後クラッシュ、主要画面が真っ白 |
| データ損失 | 保存内容の消失・上書き・復元不能 |
| 金銭・権利 | 誤課金、二重課金、契約状態の誤表示 |
| セキュリティ | 他人データ閲覧、権限外操作、認証バイパス |
| 業務停止 | 本番運用で代替手段がなく業務が止まる |
| 影響範囲 | 全ユーザーまたは主要ユーザーの大多数 |
| 再現性 | 手順が明確、または高確率で発生 |

## 優先度マッピング

| 優先度 | 目安 | issue タイトル |
|--------|------|----------------|
| **P0** | 上記のいずれかを満たし、日常利用で再現しうる | `[P0][bug]` |
| **P1** | 重大だが条件付き（障害時・複数タブ・設定依存） | `[P1][bug]` |
| **P2** | 回避策あり、影響限定、UX 回復不足 | `[P2][bug]` |

## 致命的ではないことが多いもの（対比）

- 表示のずれ、文言ミス、軽微な UI 不具合
- 再読み込み・別ルートで回避可能
- 特定条件・少数ユーザー・非本番機能のみ
- 遅いが完了するパフォーマンス低下

医療・金融・インフラ系プロダクトでは「遅延」「誤表示」も致命的扱いになりうる。監査開始時にドメイン要件を確認する。

## CONFIRMED に必要な再現性

静的コードレビューのみでは **CANDIDATE** 止まり。`CONFIRMED` には次のいずれかを必須とする:

1. **ユーザージャーニー再現** — 番号付き手順（ログイン → 画面 A → 操作 B → 期待と異なる結果）
2. **コード因果チェーン** — 入口（API/WS/UI イベント）から不具合状態までの呼び出し列（`path:Lx-Ly` 付き）

両方あると issue 品質が上がる。どちらも無い finding は起票しない。

## 監査カテゴリと典型リスク

| カテゴリ | 典型の致命的パターン |
|----------|---------------------|
| `auth-security` | 認証バイパス、平文秘密、break-glass 過剰権限 |
| `data-integrity` | 非原子的多段書き込み、削除順序誤り、last-write-wins |
| `core-availability` | コア API/WS 停止、単一障害点で主要フロー不能 |
| `ux-recovery` | 失敗がサイレント、誤ったログアウト表示、二重破壊的操作 |
