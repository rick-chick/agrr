## 1. プロダクトの方向性（観測から導いた現状の合意事項）

### 1.1 一文定義

> 気象 × GDD（積算温度）× 最適化で、農業の**作付け計画**を立て、**実行を記録**し、**実績から学んで次の計画に返す**閉ループを提供する。フル農場 ERP ではない。

| 根拠 | 出典 |
|------|------|
| プロダクト芯は「農業計画支援（気象 × GDD × 最適化）。フル農場 ERP ではない」 | `.cursor/skills/product-gap-to-issues/SKILL.md` |
| ホーム: 「気象とGDDで、作付け計画を可視化」 | `frontend/src/assets/i18n/ja.json` `home.index.hero` |
| 会計・在庫・販売などは計画芯との接続が弱い限り優先度を下げる（ERP 化リスク） | `.cursor/skills/product-gap-to-issues/references/breadth-depth-scale.md` |
| 計算は agrr デーモン、生成（LLM）は外部スキル。内蔵 AI は廃止方針 | [ADR-001](adr/ADR-001-external-skill-generation-agrr-daemon-calculation.md) |

### 1.2 価値の 3 層

| 層 | 内容 | 実装状況（観測） |
|----|------|------------------|
| **計画** | 公開ウィザード / 私有計画、ガント、作付け適期（entry-schedule）、作物マスタ（ステージ・GDD・作業テンプレ） | 本番稼働。entry-schedule は fail-closed（agrr GDD 進捗のみで判定、#1278） |
| **実行** | 作業ハブ `/work`、作業記録（GDD・気象スナップショット・施肥/防除/収穫の構造化）、天候トリガー型リスケ提案 | 実装済み（#792, #1000, #1049 系） |
| **学習** | 計画 vs 実績の乖離、`/plans/:id/learn` の提案キュー、一括適用 → 再最適化パイプライン、次計画への carryover | 実装済み（#800, #835, #920, #1092 系） |

### 1.3 獲得〜定着ファネル

```
SEO（research レポート・entry-schedule・sitemap）
  → 公開プラン（匿名: 地域 → 作物 → 最適化 → 結果）
  → save（ログイン）→ 私有計画・オンボーディング
  → 作業記録 → 学習 → 再最適化
```

ファネル計測の基盤（GA4 J3 最適化失敗・復帰イベント、#1321）が入り始めた段階。

### 1.4 プラットフォーム / B2B の布石

| 布石 | 状態 |
|------|------|
| 外部スキル + `setup_proposal` + 公式 MCP + API キー（スコープ・レート制限） | 完了（#316 系）。内蔵生成 API は Sunset **2026-10-18** 予定 |
| Organization（B2B テナント土台）ADR-002 | Phase 1 完了（スキーマ・CRUD・memberships API・personal org・org スコープ認可、#604 系）。**フロント UI・クォータ・SSO/SCIM/監査は未着手** |

### 1.5 開発運用の現在地（方向性に影響する事実）

| 観測 | 数値・事実 |
|------|------------|
| open issue | **0 件**（`gh issue list --state open`） |
| 2026-09-03 以降にマージされた PR | 38 件中 **25 件が `test:`**、feat/fix は 13 件。9/17 以降にマージされた 12 件はすべて `test:` |
| 開発の駆動 | issue → Cloud Agent → PR → 自動マージの自動化パイプライン。**バックログ が空だと、価値の低い test 追加が継続的に生成される** |

**解釈**: 基盤の堅牢化（8 月）と entry-schedule の深化（9 月）が一段落し、**次に何を積むかを決める入力（方向性）が不足している**。本ロードマップはその入力である。

## 2. 戦略テーマ（優先順）

判断軸は「計画芯（気象 × GDD × 最適化）に効くか」「計画→実行→学習の閉ループを厚くするか」。幅より深さを先に取る（`breadth-depth-scale.md` のコア 5 観点の評価に基づく暫定判定。§3 の回答で覆りうる）。

| # | テーマ | 目的 | 幅/深さ |
|---|--------|------|---------|
| T1 | **計測できる状態にする** | ファネル・定着・失敗復帰を数値で判断できるようにする（現状は数値なしで機能追加が続いている） | 深さ |
| T2 | **閉ループの定着** | 「初回の計画作成」で終わらず、記録 → 学習 → 再最適化まで回る利用者を増やす | 深さ |
| T3 | **計画芯の信頼性** | 最適化・気象取得の成功率と結果の説明可能性。fail-closed 方針の維持 | 深さ |
| T4 | **獲得の量産** | entry-schedule / research の SEO 資産を作物・地域に拡張し、公開プランへ接続 | 幅（既存資産の延長） |
| T5 | **プラットフォーム完了と API 価値化** | 内蔵生成の削除、MCP/スキルの利用拡大、課金 tier（スコープ）の要否判断 | 幅 |
| T6 | **B2B（Organization）の顕在化** | 需要検証後にのみ UI・クォータ・共有を出す | 幅（要検証） |
| T7 | **運用基盤の上限管理** | SQLite 単一書き手・Cloud Run 単一インスタンスの限界に対する発動条件を定義 | 基盤 |

## 3. 要確認事項（作業を進める前に人間が決めること）

コード・doc・issue から**決められなかった**論点。回答により T4–T6 の優先度が変わる。

| # | 論点 | 観測された矛盾・不足 | 選択肢 |
|---|------|----------------------|--------|
| Q1 | **主対象ユーザー** | デモは「サンプル市民農園」、運営者情報は市民農園の栽培経験（個人運営）。一方 ADR-002 は法人・チーム共有（B2B）を志向 | (a) 家庭菜園・市民農園・小規模農家を主対象 / (b) 法人・チームを主対象 / (c) (a) で獲得し (b) は API・org で後続 |
| Q2 | **収益モデル** | About は「基本機能は無料」＋ Google AdSense。課金コードなし。API ドキュメントは「将来の課金 tier」を示唆 | (a) 広告のみ / (b) API・org を有償 / (c) 当面は収益化しない（利用拡大優先） |
| Q3 | **成功指標（North Star）** | 定義された KPI がない。SLO は信頼性のみ（`ops/core-api-optimization-sli-slo.md`） | 例: 週次で作業記録を残した私有計画数 / 公開プラン→save 転換率 / 学習提案の適用数 |

| Q5 | **Sunset 実行方針** | #323（内蔵生成の削除）は 2026-07-19 に COMPLETED でクローズされたが、`ai_api.rs` の `ai_create`/`ai_update`、`masters_crop_task_schedule_blueprints.rs` の `regenerate` は**現存**。Sunset は 2026-10-18 | 予定どおり 10/18 以降に削除する場合は追跡 issue を再作成する |

| 項目 | 内容 | 出口条件 |
|------|------|----------|

### Phase 1 — 計測基盤（T1）

依存: Phase 0-1 の Q3（指標の定義）。

| 項目 | 内容 | 出口条件 |
|------|------|----------|
| 1-1 | 指標の定義と計測点の棚卸し: 公開プラン開始 → 結果表示 → save → 初回作業記録 → 初回学習適用 | 各段階のイベント/クエリが存在し、定義が doc 化 |
| 1-2 | GA4 UX イベント（J3 基盤 #1321）を J1・J2・J4 に横展開 | 主要ジョブごとに失敗・復帰・離脱が観測可能 |
| 1-3 | 週次の指標スナップショット（本番レプリカの読み取り専用クエリ: `production-primary-sqlite-query` スキル）の手順化 | 週次で同じクエリが再実行できる |
| 1-4 | SLO 実績の月次記録を開始（`ops/core-api-optimization-sli-slo.md` のレビュー頻度に従う） | 直近 1 回分の実績記録 |

### Phase 2 — 閉ループの定着（T2）と計画芯の信頼性（T3）

依存: Phase 1 の計測で「どこで離脱するか」が見えていること（推測で機能を足さない）。

| 項目 | 内容 | 出口条件 |
|------|------|----------|
| 2-1 | 公開プラン → save → 私有計画 → 初回作業記録の**離脱点の改善**（1-1 の計測で最大の離脱を特定してから issue 化） | 該当ステップの転換率が改善（ベースライン比） |
| 2-2 | 学習提案の**適用率**を上げる（提案の根拠表示・確認負荷の低減。既存の learn 画面の深化であり新画面は作らない） | 提案 → 適用の転換が計測可能で、改善が確認できる |
| 2-3 | 最適化・気象取得の**失敗分類と復帰率**（ALERT-OPT-FAIL の運用、J3 イベントの分析結果を反映） | 最適化完了率 SLO 95% の達成状況が月次で可視 |
| 2-4 | 作物マスタの**計画可能率**（ステージ・GDD・作業テンプレが揃った作物の割合）を上げる。外部スキル（MCP/`setup_proposal`）で参照作物を拡充 | 参照作物のうち計画可能なものの割合が計測・改善 |
| 2-5 | fail-closed 方針（`.cursor/rules/fallback.mdc`）を新規判定ロジックのレビュー基準として維持 | 新規のドメイン判定にフォールバックがない |

### Phase 3 — 獲得の拡張（T4）とプラットフォーム（T5）

依存: Phase 1（計測）。T4 は Q4（対象地域）。

| 項目 | 内容 | 出口条件 |
|------|------|----------|
| 3-1 | entry-schedule の作物・地域カバレッジ拡大（プリレンダ・sitemap・固有メタは既存の基盤を再利用） | 追加ページが GSC で index され、公開プランへの流入が計測可能 |
| 3-2 | research レポートから公開プランへの CTA の効果測定と改善 | CTA 経由の公開プラン開始数が計測可能 |

### Phase 5 — 運用基盤の上限管理（T7、トリガー駆動）

継続的に監視し、**トリガー到達時に**着手する。先回りで移行しない。

| トリガー例（Q6 で確定） | 対応候補 |
|--------------------------|----------|

## 5. やらないこと

| 項目 | 理由 |
|------|------|
| 会計・在庫・販売などの農場 ERP 機能 | 計画芯との接続が弱く、ERP 化リスク（§1.1） |
| 内蔵 LLM 生成の維持・再導入 | ADR-001。生成は外部スキル |
| 計測なしの新画面追加 | 離脱点の実測が先（T1 → T2） |
| 需要未検証の SSO/SCIM 先行実装 | Phase 4 のゲート |
| 網羅目的のみの test 追加 | 現在のマージ PR の過半。バグ検出・仕様固定の根拠がある test のみ追加する |

## 6. 更新ルール

- §3 の回答後に本書を確定版へ更新し、Phase ごとに epic → 子 issue を起票する（`product-gap-to-issues` スキルの G2/G3 を通す）。
- フェーズの出口条件を満たしたら該当行を更新する。判断（Q2 など）は ADR に昇格する。
- 本書は**方針の正本**であり、実装詳細・issue 本文は複製しない。
